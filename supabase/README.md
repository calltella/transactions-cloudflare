# Supabase の初期導入

Supabase 自体（クラウドプロジェクトまたはローカルの Supabase）が起動していれば、
次の **いずれか1本を全文実行** するだけでアプリ用DBを構築できます。
テーブルを先に作ったり、個別SQLを順番に実行したりする必要はありません。

| 環境 | 実行するSQL |
| --- | --- |
| 本番・リモート | [production/setup.sql](production/setup.sql) |
| 開発・Docker | [local/setup.sql](local/setup.sql) |

Supabase SQL Editor にファイルの全文を貼り付けて実行してください。
psql を使う場合は、接続先を対象環境に設定して次のように実行できます。

```sh
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/local/setup.sql
```

管理者は Supabase Auth の `app_metadata.role = "admin"` で判定します。
固定ユーザーIDや `DEVELOPER_USER_IDS` の設定は不要です。
管理者の設定手順は [管理者設定](#管理者設定) を参照してください。
SQLはログインユーザーや認証キーを作成しません。
アプリの接続URL・キーなどの環境変数は別途設定します。

## 作成するもの

- CSV作業テーブル `transactions_work`、取引テーブル `transactions`
- 種別・支払方法・親カテゴリ・子カテゴリのマスター
- カード設定 `credit_cards`、銀行口座設定 `bank_accounts`
- 月の集計期間・休日調整設定 `dashboard_settings`
- RLS、アクセス権限、インデックス、更新日時トリガー
- 正規化3関数、取引登録関数、口座間振替の登録・削除関数
- 初期種別「収入」「支出」

全体を1トランザクションで適用します。途中で失敗した場合は全体をロールバックします。
同じSQLを再実行しても既存の取引・設定を削除しません。
正規化・取引登録・振替の関数を定義しますが、導入SQLから実行はしません。
CSVの取込とマスターの正規化は、導入後にアプリから行ってください。

## SQLの管理

`schema.sql` に初期テーブルとカード設定を定義し、必要な最新版のマイグレーションを
結合して、環境別の `setup.sql` を生成しています。
過去の修正版を重ねて適用する必要はありません。`migrations/` と既存の
`local/normalize_*.sql` は、既存環境の個別更新・履歴確認用として残しています。

元のSQLを変更した場合は、次を実行して統合SQLを更新してください。

```sh
npm run supabase:setup
npm run supabase:setup:check
```

開発用DBに接続できる環境では、次のコマンドで両方の統合SQLを検証できます。
一時DBを作成して、初回導入・再実行時のデータ保持・正規化・取込・カード・振替・
アクセス制限を確認したあと、一時DBを削除します。開発用DBの既存データには変更を加えません。
DB作成権限のある `.env.development.local` の `DATABASE_URL` が必要です。

```sh
npm run supabase:setup:verify
```

## 管理者設定

管理者にする既存の Supabase Auth ユーザーへ、次の **app_metadata** を設定します。
既存のメタデータは残して `role` を追加してください。

```json
{ "role": "admin" }
```

SQL Editor から設定する場合は、下記の `対象ユーザーのUUID` を Authentication に表示される
実際のユーザーIDへ置き換えて実行してください。初期導入SQLは管理者を自動付与しません。

```sql
update auth.users
set raw_app_meta_data = coalesce(raw_app_meta_data, '{}'::jsonb)
  || '{"role":"admin"}'::jsonb
where id = '対象ユーザーのUUID'::uuid;
```

取り消す場合は、同じユーザーの `role` を削除します。

```sql
update auth.users
set raw_app_meta_data = coalesce(raw_app_meta_data, '{}'::jsonb) - 'role'
where id = '対象ユーザーのUUID'::uuid;
```

画面とサーバーアクションは `auth.getUser()` が返す最新の `app_metadata` を使います。
SQL関数と種別マスターの書き込みポリシーは `private.is_admin()` で Auth の現在の値を参照します。
JWTに残っている古い管理者情報だけでは操作できません。`user_metadata` に同じ値を
入れても管理者にはなりません。管理者権限は開発・データ管理画面、DB診断、正規化と
取引登録に適用し、通常の取引や口座の所有者RLSは維持します。

既存環境の切替は `migrations/20261013200858_auth_app_metadata_admin.sql`、
または対象環境の最新 `setup.sql` を実行してください。
管理者のメタデータを設定した後、画面を再読み込みしてください。

## 銀行口座の新規登録

「銀行口座」→「銀行口座を登録」（`/bank-accounts/new`）から、CSVの取込前でも口座を登録できます。
口座名・銀行名・支店名・口座名義・開始残高と基準日・利用状態・メモを保存し、
登録後は取引履歴へ移動します。一般のログインユーザーも自分の口座を登録できます。
口座名が既存の銀行の支払方法と同じ場合は、その支払方法に自分の口座を登録します。
自分の口座が設定済みなら重複エラーとし、既存設定は上書きしません。
別の種別（カードなど）で使われている名前は登録できません。

支払方法と口座情報を同時に保存する `create_bank_account` 関数は統合SQLに含まれています。
既存環境へ追加する場合は `migrations/20261013204354_create_bank_account.sql` を適用してください。

## 銀行口座・カードの並び替え

ダッシュボードの銀行口座・クレジットカード欄、または各設定画面の「並び替え」から
上下ボタンで順序を変更して保存できます。利用中のものだけ表示するダッシュボードと、
設定画面・口座選択に保存した順序を反映します。新規登録したものは末尾に表示します。
並び順はユーザーごとに保存し、他ユーザーの設定は変更できません。
既存環境には `migrations/20261013205800_account_display_order.sql` を適用してください。
初回導入の統合SQLにも含まれています。

## 月初金額・繰越金

銀行口座の取引履歴で対象月を選び、「月初金額・繰越金」から登録します。
前月からの繰越金を手動登録すると、その金額を月初金額として使います。
翌月に保存済みの設定がなければ、その月の月末残高を自動で繰り越します。
「月初金額を個別に指定する」を選ぶと、指定した金額を優先します。0円の指定も可能です。
繰越金を別行で加算しないため、二重計上しません。繰越金も個別指定もなければ0円です。
繰越金を取り消す場合は0円で保存します。翌月に設定がなければ、前月までの設定額・入出金・カード引き落としを集計して月末残高を自動で繰り越します。

設定は口座・対象月・ユーザーごとに保存し、通常の収入・支出取引には登録しません。
ダッシュボードも現在の対象月の月初金額（繰越金または個別指定）＋実際の入出金で計算します。
過去の口座設定の開始残高・基準日は保存したまま、月初金額には自動反映しません。
既存環境には `migrations/20261013210505_bank_monthly_balances.sql` を適用してください。
統合 `setup.sql` にも含まれています。

## カード明細の翌月処理

カード利用明細の鉛筆ボタンから「翌月処理（次の締め期間に含める）」を選んで保存します。
利用日はそのまま保持し、カードの締め日から計算した次の締め期間へ移します。
その明細は元の支払月の一覧・予定額から外れ、次の支払月へ入ります。
ダッシュボードと銀行口座の引き落とし予定も同じ条件で計算します。
通常の処理に戻す場合はチェックを外して保存してください。
既存環境には `migrations/20261013214908_card_deferred_billing.sql` を適用してください。
統合 `setup.sql` にも含まれています。

月初金額の繰越金連動・個別指定への変更は `migrations/20261013221205_monthly_opening_override.sql` を適用してください。既存の0円以外の月初金額は個別指定として引き継ぎます。
